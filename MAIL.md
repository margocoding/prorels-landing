# Заявки с лендинга ПроРельс

Форма на главной и под каждой статьёй: электронная почта, телефон, комментарий и подтверждение согласия на обработку данных. Получатель фиксирован: **zakaz@prorelsa.ru**. Приложения к заявке отправляются по прямой почтовой ссылке; загрузки файлов в API нет.

`POST /api/contact` работает в Node.js runtime Next.js. SMTP-параметры читаются на сервере при отправке. Письмо содержит оформленную HTML-версию и обычный текст, номер заявки, время по Москве, контакты, комментарий, название и адрес страницы, UTM-метки текущего URL. В `Reply-To` ставится адрес клиента; ответ в почтовой программе направляется ему. UTM показываются как переданные браузером сведения и не заменяют аналитику.

## Подключение на сервере

Заполните переменные из `.env.example` через окружение процесса или `env_file` в Docker Compose:

```dotenv
SITE_URL=https://prorels.com
SMTP_HOST=smtp.timeweb.ru
SMTP_PORT=465
SMTP_USER=zakaz@traer.ru
SMTP_PASS=
SMTP_FROM=zakaz@traer.ru
CONTACT_TRUST_PROXY=false
```

Это параметры Timeweb, предоставленные для prorels.com; пароль заполняется только на сервере. `SMTP_FROM` — один адрес почтового ящика, разрешённого провайдером для отправки; имя «ПроРельс — заявки» добавляется приложением. Отправитель `zakaz@traer.ru` отличается от получателя `zakaz@prorelsa.ru` — это ожидаемая конфигурация. Для порта 465 используется TLS; для остальных портов, обычно 587, обязателен STARTTLS с проверкой сертификата. Для провайдера настройте его рекомендуемые SPF/DKIM и пароль приложения, если требуется.

SMTP-секреты задаются только при запуске: не передавайте их в build args, не добавляйте `NEXT_PUBLIC_` и не коммитьте env-файл. После изменения SMTP перезапустите приложение. `SITE_URL` задайте также во время запуска, чтобы проверка Origin и адрес источника соответствовали публичному домену. Для метаданных этот же домен и `SITE_INDEXABLE` нужны **при сборке** — см. README.

В контейнере приложение слушает порт 5000. Пример с уже собранным образом и env-файлом на сервере:

```sh
docker run --env-file .env.production -p 127.0.0.1:5000:5000 prorels-landing
```

Обратный прокси должен сохранять публичный `Host`, передавать правильный протокол HTTPS и направлять `/api/contact` в то же приложение. После подключения выполните одну согласованную проверку из публичной формы: письмо должно появиться в настоящем ящике, содержать публичный адрес страницы и правильный адрес для ответа. Принятие письма SMTP-сервером не гарантирует попадание во «Входящие» — результат зависит также от провайдера и настроек домена.

API принимает Origin основного домена из `SITE_URL` и его варианта с `www` с тем же протоколом и портом. Остальные поддомены и сторонние сайты отклоняются. В письмо попадает адрес страницы, с которой действительно отправили форму. Для SEO на прокси рекомендуется перенаправлять `www.prorels.com` на `prorels.com`.

Файл `.env` рядом с `compose.yml` сам по себе не передаёт SMTP в контейнер. Подключите его в нужном сервисе через `env_file: .env.production` или перечислите переменные в `environment`. После изменения настроек пересоздайте контейнер командой `docker compose up -d --force-recreate`. Не включайте `SMTP_LOCAL_TEST` для Timeweb.

## Проверка реального SMTP без отправки письма

Из корня проекта, с закрытым файлом окружения:

```sh
node --env-file=.env.production --input-type=module -e "import nodemailer from 'nodemailer'; import { smtpSettings } from './src/lib/lead-mailer.ts'; const transport = nodemailer.createTransport(smtpSettings(process.env).transport); try { await transport.verify(); console.log('SMTP connection and authentication OK; no email sent.'); } catch (error) { console.error('SMTP verification failed', { code: error.code, responseCode: error.responseCode }); process.exitCode = 1; } finally { transport.close(); }"
```

Команда проверяет соединение, TLS и авторизацию. Она не проверяет существование адреса получателя и попадание письма во входящие. На 11.10.2026 соединение и авторизация `smtp.timeweb.ru:465` с предоставленными настройками прошли. Секреты в репозиторий не добавлены.

## Ошибки и ограничения

- Без настроенного SMTP возвращается 503; интерфейс сохраняет введённые поля и предлагает почту/телефон. Фиктивного успешного ответа нет.
- Сервер проверяет контакты, длину комментария, согласие, Origin, JSON и размер тела до 24 000 байт. Неизвестные страницы источника отклоняются, получателя нельзя подменить запросом.
- Пользовательский текст экранируется в HTML; заголовки не берутся из комментария. Данные заявки и SMTP-секреты не записываются в логи. В базе заявки не сохраняются.
- Есть скрытое поле для простых ботов и лимит 5 попыток за 15 минут для клиента, 60 для процесса. По умолчанию клиент определяется по хешу почты. `CONTACT_TRUST_PROXY=true` переключает на `X-Real-IP`, только если доверенный прокси перезаписывает этот заголовок и прямой доступ к приложению закрыт.
- Счётчики хранятся в памяти одного процесса и сбрасываются при перезапуске. Для нескольких реплик или заметного спама добавьте общий лимитер на прокси/в хранилище. CAPTCHA и очередь повторной отправки не подключены.

## Автоматическая проверка без внешних писем

```sh
npm test
npm run build
npm run verify:contact
```

Проверка запускает отдельный экземпляр standalone и SMTP-приёмник на свободных loopback-портах. Проверяет реальный SMTP-обмен, адрес получателя, Reply-To, HTML/текст, источник, UTM, некорректные запросы, лимиты, отказ почтового сервера и отсутствие конфигурации. `SMTP_LOCAL_TEST=true` допускает незашифрованный SMTP только для `127.0.0.1` или `::1` и используется исключительно локальным тестом; на публичном сервере его не задавайте. Компонентный тест проверяет валидацию, блокировку повторного нажатия, сохранение текста при ошибке и очистку только после успеха.
